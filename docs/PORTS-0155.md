# Automatic port allocation

New Minecraft Bedrock, Node.js and Python servers use automatic ports by default. Bedrock clones receive a separate allocation on their source VPS. The selected VPS makes the decision when the request is accepted; the browser does not reserve a suggestion. The returned server and connection address show the assigned ports. Existing servers retain their current ports.

For new compatible Bedrock servers the panel uses NetherNet and prefers 19132 only when its complete allocation is free. Other allocations use cryptographic randomness within 20000–59999 and exclude the operating system's current ephemeral-port interval and explicitly reserved host ports. Native Ubuntu allocation reads local TCP/UDP socket tables for IPv4/IPv6 and checks persisted servers, stopped/installing servers and pending network changes. Bedrock allocation includes its primary/IPv6 ports and the complete NetherNet UDP range where required. Automatic allocation conservatively avoids numeric overlap across those reservations. Allocations are scoped to one VPS: separate IP addresses can use the same port number.

Selection and registration run through the node's admission lock. An owned pending reservation remains in place while native bind checks await, then the accepted server record retains the allocation. A failed request releases its temporary reservation. An unreadable or malformed socket inventory and exhaustion return an explicit error before a server/job is created; they do not silently choose a fixed default. Concurrent creates must receive different allocations or a clear capacity/allocation error.

Advanced custom ports remain available. Explicit legacy API ports retain their existing protocol-aware validation; TCP and UDP are separate network namespaces. Automatic requests omit numeric port fields and use `portAllocation:"auto"`; a request mixing automatic allocation with explicit ports is invalid. Older agents without the capability must be updated before automatic allocation can be used; custom allocation remains the compatible option.

Socket-table reads and bind checks establish availability at the time of admission. They cannot permanently prevent an unrelated operating-system service from claiming a port later. Startup therefore retains native bind checks and reports a conflict; it does not silently change an established connection address. An accepted allocation is a panel reservation, not a firewall rule or proof of public reachability. Existing network-access controls still apply.

Implementation references: [Linux ephemeral and reserved port policy](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html) and [Node.js cryptographic random integers](https://nodejs.org/download/release/v22.18.0/docs/api/crypto.html#cryptorandomintmin-max-callback). The panel reads the host policy and does not change those sysctls.

## NetherNet on a VPS behind NAT

NetherNet uses a TCP signaling port and a separate UDP peer range. Its `server-portv6` property does not provide a second independent listener. The panel reserves and displays the complete required network; two numeric ports alone are not sufficient.

For new servers and clones, a configured public IPv4 that is absent from the local NIC, together with a private RFC1918 IPv4 NIC, produces an explicit same-port mapping in `server-udp-ports`: `PUBLIC_IPV4:EXTERNAL_RANGE:INTERNAL_RANGE`. The main panel uses a literal IPv4 from `PUBLIC_URL`, or the optional `VORTEX_GAME_PUBLIC_IP` environment setting. Linked workers receive the selected node’s configured public IPv4 through the authenticated control plane. Fresh manual worker installation also supports `--game-public-ip IPV4`. DNS names and shared/unknown NAT are not guessed; custom mappings remain available.

Existing servers and custom mappings remain unchanged during updates or unrelated settings edits. Regenerating an automatic network explicitly uses the current node context. Creating/cloning and starting Bedrock reconcile only scoped panel-owned rules when an active host firewall can be managed safely. Inactive or unavailable firewalls produce a warning; an active manageable firewall that cannot confirm the ports blocks startup. Deleting a server removes only its owned rules, with a visible warning if cleanup cannot be verified. Provider security lists, port forwarding and external reachability must still be configured separately.
